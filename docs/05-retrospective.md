# 最难问题、收获与下一步

## 实现中最难的问题

难点是把模型建议与业务事实区分开。模型可以选择替代时间，也可以误报成功，但只有工具能确认草稿已写入，只有调用方明确确认才能批准硬性时间变更。因此最终结果必须从真实工具状态生成，不能照抄模型终态文本。

防重也不能只查已有记录后再插入：两个请求可能同时看到空闲。项目使用 SQLite 写事务、保存前复查和唯一约束避免查询与保存之间的竞争。

## 本次实现得到的工程认识

- ReAct 的证据是模型读到不同工具结果后实际选择不同动作，代码里存在循环本身不够。
- Mock 可高效检验异常路径，但无法证明真实模型决策质量。
- 未完成、待确认、保存失败与已保存必须分别表达；只写一个 success 字段容易掩盖风险。
- 测试应直接检查数据库数量和保存回执，而不只是核对模型文字。

这些是对实现的技术复盘，不替代考生本人反思；考生应补充自己最难理解的部分、亲自修改内容和实际学习收获。

## 下一步优先级

1. 在已完成的 10 组真实服务场景基础上做多次稳定性验证，尤其保留冲突场景提前 finish 的错误与纠正。
2. 完成草稿确认、更新、撤销与版本关联，避免修订请求留下旧占位。
3. 增加生产规则来源、审批鉴权、可变时长时段、脱敏与审计。
4. 需求确实出现时再考虑批量优化、异步 Runtime 或框架迁移。
