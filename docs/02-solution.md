# 调用流程、动态决策与技术取舍

## 流程

CLI 验证输入 → 初始化模型和工具 → 模型选择一个 JSON 动作 → 严格校验动作格式 → 工具执行 → 将实际结果加入历史 → 再次请求模型 → 模型结束或达到上限。

每次模型输入包含原始请求和截至当时的完整工具历史；输出只包含 action、arguments、简要 reason。执行器没有按场景安排固定下一步。MockModel 单独实现固定测试策略，仅用于离线验证工具与循环。

工具：`read_material()`、`lookup_metadata()`、`check_rules()`、`query_slots()`、`save_draft(slot)`；`finish(status, reason)` 为终止动作。最大决策步数默认为 12，含 finish 和非法动作；工具调用数不超过决策数。模型网络调用单次有超时，不自动重试。

## 决策差异

- 无风险且原时间可用：检查 → 查询 → 保存原时间。
- 信息缺失：模型可选择补查 → 重查规则 → 继续或请求补充。
- 风险：模型应选择阻断；工具也会拒绝绕过审核直接保存。
- 原时间冲突：模型选择替代时间；工具自动将未获确认的硬性变更记为 pending。
- 保存返回冲突：模型可以重新查询再选择；工具不会替模型自动重试。
- 保存失败：模型可结束 failed；没有回执便不能返回成功。

这些是预期行为，实际动作以 Trace 为准；离线策略不能证明模型会做出这些决策。

## 数据与状态保护

`request_id + material_id` 是业务幂等键，完整规范化请求的 SHA256 防止相同键绑定不同意图。SQLite 的 `BEGIN IMMEDIATE`、业务键唯一约束、渠道/时间唯一约束共同防重和防冲突，保存事务再次检查占用，避免查询后竞争。重复保存返回原草稿 ID 与实际存储内容，不接受模型提供的保存结果。

审核必须通过且时段已查询可用，保存才有权限。补查只填缺失字段，不覆盖既有风险内容；补查后审核失效，必须重新检查。请求在模型接口中只读，工具不接受自定义频道、确认状态、发布时间要求或发布动作。

终态由实际工具状态投影：草稿回执决定 saved/existing；未保存则模型不能完成成功状态；待确认草稿不能被模型 finish 宣称为已确认。即便执行上限在保存后到达，也返回 incomplete，但保留真实保存状态，便于后续核对。

## 取舍

Python 3.12 标准库、SQLite，无第三方 Agent 框架及版本依赖。手写循环便于在有限时间内解释每次动作和权限边界，代价是没有框架自带的追踪、检查点或复杂并发能力。

真实模型支持兼容 Chat Completions JSON 输出，以及 Ollama `/api/chat`；这两种模式不包含预设业务决策。模型无效 JSON、超时或网络失败返回 failed，并保留此前已完成的工具记录，不降级为 Mock。采用严格 JSON 避免对任意文本进行宽松猜测，部分服务可能需要调整协议适配器。

参考：[Ollama Chat API](https://docs.ollama.com/api/chat)，2026-10-30 核对。没有采用 Agent 框架，因此无框架承担的隐藏业务职责。
